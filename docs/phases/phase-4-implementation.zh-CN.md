# 阶段 4 源码实现分析：定义 XMachine，并让 XCPU 逐条执行指令

> 对应提交：`阶段4：实现 XMachine 与 XCPU 指令执行`
>
> 核心源码位于 `xlangvm/src/main/java/com/xlang/vm/`，重点阅读 `Opcode`、`XCpu`、`XMachine`、`Assembler` 与 `HexProgram`。

## 1. 这阶段不是“模拟一台电脑外观”

阶段 4 定义的是 Instruction Set Architecture（ISA）：程序可见的寄存器、指令编码、内存读写规则、标志位以及调用/返回约定。`XMachine` 则用 Java 解释这些规则。

ISA 与微架构要区分：ISA 规定 `ADD` 的可见效果；真实处理器可用流水线、乱序执行等不同内部方式实现同一效果。RISC-V 规范也明确把 ISA 与具体实现分开，并以指令可见行为作为软件/硬件接口，参见 [RISC-V Unprivileged ISA](https://docs.riscv.org/reference/isa/unpriv/rv32.html)。

XMachine 是教学型 ISA 的软件实现，不试图模拟晶体管或时钟周期。

## 2. 一条指令从字节变成行为

核心是 fetch-decode-execute 循环：

```text
PC 指向下一条指令
  |
  v
fetch opcode byte
  |
  v
decode Opcode 与操作数
  |
  v
预先推进 PC 到顺序后继
  |
  v
execute：改寄存器/标志/内存/PC
  |
  v
记录 trace，进入下一步
```

`XMachine.run(...)` 重复单步执行，直到 `HALT`、故障或超过步数限制。步数上限防止错误程序死循环把测试永远挂住。

## 3. `Opcode` 为什么是“单一事实来源”

`Opcode` 把操作码数值、助记符和指令大小集中定义。Assembler、Decoder 和 trace 都应引用同一份定义。

若编码表散落在多个 switch 中，很容易出现“汇编器认为 opcode 3 是 ADD，CPU 却认为是 SUB”。集中建模使重复编号、未知操作码和长度不一致更早暴露。

固定指令大小信息还有一个实际用途：CPU 在执行前可以检查整条指令是否越过内存边界，而不是读到一半才失败。

## 4. `XCpu` 与 `XMachine` 为什么分开

`XCpu` 只保存处理器状态：

- 通用寄存器；
- program counter (`pc`)；
- 比较产生的标志；
- halted 状态；
- 已执行步数。

`XMachine` 拥有内存并实现指令语义。分离后，CPU 状态可以快照、打印和复位，内存访问规则也能在阶段 5 被 XOS 接管，而不必重写寄存器模型。

“CPU 发地址请求”和“内存系统如何满足请求”本来就是两个概念层。

## 5. 为什么先推进 PC，再执行指令语义

普通指令应自然落到下一条，因此 Decoder 读完当前指令后，先把 `pc` 设为顺序后继。大多数 opcode 不再单独修改 PC；只有 jump、call、return 等控制流指令覆盖它。

这个约定特别简化 `CALL`：压栈的返回地址正好是已经计算好的“下一条指令地址”。如果 PC 仍指向 CALL 开头，每个控制流实现都要重复计算当前指令长度。

前提是执行前已做完整边界检查；否则“推进后出错”会让故障现场难以解释。

## 6. 算术、比较与分支为何分成不同指令

算术指令读取寄存器/立即数，计算后写回目标寄存器。比较指令不直接跳转，而是设置 CPU 标志；条件跳转再读取这些标志决定是否改写 PC。

这种设计把：

1. 产生比较结果；
2. 根据结果改变控制流；

分成两步。阶段 6 的后端可用同一次 `CMP` 配合不同分支指令表达 `<`、`==` 等控制流。它类似许多真实 ISA 的 condition flags 思路，但 XMachine 只保留教学所需的最小状态。

## 7. 栈、`CALL` 和 `RET`

栈由一个约定的 stack pointer 寄存器指向。`PUSH` 调整 SP 并写入值，`POP` 读取后恢复 SP。

`CALL target` 的语义近似：

```text
push(next_pc)
pc = target
```

`RET` 则：

```text
pc = pop()
```

这只解决“回到调用者哪里”，还没有解决参数、局部变量、返回值和保存寄存器。完整 calling convention 会在阶段 6 由后端建立。

## 8. 端序为什么必须明确

XMachine 用 little-endian 编解码多字节整数：低有效字节放在低地址。端序不是 Java 实现细节，而是目标机器 ABI 的一部分；编译器、目标文件重定位、链接器和虚拟机必须一致。

例如十六进制值 `0x12345678` 写入连续四字节后，低地址到高地址依次是 `78 56 34 12`。阶段 7 的 ABS32 重定位也必须用同一顺序打补丁。

## 9. 边界检查与 `MachineFault`

模拟器不能依赖 Java 数组自然抛出的异常，因为那只能说“索引越界”，不能说明是非法寄存器、截断指令还是机器内存越界。

`XMachine` 主动验证：

- opcode 是否存在；
- 指令的全部字节是否可取；
- 寄存器编号是否合法；
- 数据访问地址和宽度是否有效；
- 栈操作是否越界。

失败统一转为带机器语义的 `MachineFault`。这是建立清晰抽象边界：用户程序的机器故障不应泄漏成宿主 JVM 实现异常。

## 10. `Assembler` 与 `HexProgram` 为何此时就出现

阶段 4 尚无后端，仍需要一种可靠方式构造机器程序。

- `Assembler` 用助记操作构造正确编码，适合单元测试；
- `HexProgram` 读写十六进制文本，适合 CLI 与人工实验。

如果测试都手写字节数组，一处立即数端序错误就会被误判成 CPU 错误。小型 assembler 是测试夹具，也是 ISA 的可执行文档。

## 11. Trace 为什么记录“执行后状态”

每步 trace 包含指令位置、解码结果和状态快照，能回答“哪条指令把寄存器改坏了”。采用一致的执行后快照，观察者可以直接看到本指令造成的变化；只要文档明确，执行前也可行，最忌混用。

Trace 属于可观察性，不改变机器语义。后续 syscall 与 relocation 也沿用同样思想：把黑盒步骤变成可核对证据。

## 12. 当前机器刻意简化了什么

- 没有流水线、缓存、中断与并发；
- 当前直接使用平坦内存，尚无虚拟地址；
- 指令集和寄存器数量很小；
- flags 只支持当前分支需求；
- 没有真实硬件保护级别。

简化不是随意：它保留了编译器后端真正需要面对的 ISA、寄存器、栈、控制流、端序和故障边界。

## 13. 建议你亲手验证

1. 用 Assembler 写 `MOV/ADD/HALT`，逐步对照 PC 与寄存器。
2. 查看 CALL 前后的 SP、栈内容和返回地址。
3. 构造未知 opcode 与截断立即数，比较 `MachineFault`。
4. 手工写入 `0x12345678`，检查四个内存字节。
5. 写一个无限跳转程序，观察 step limit 如何保护运行器。
