# 阶段 2 源码实现分析：类型检查、名字绑定与词法作用域

> 对应提交：`阶段2：实现类型检查与词法作用域`
>
> 核心源码位于 `xlangc/src/main/java/com/xlang/compiler/sema/`，入口是 `TypeChecker`。

## 1. 为什么 Parser 之后还需要语义分析

下面三段代码都可能符合文法，却不一定有意义：

```xlang
unknown + 1;       // 名字不存在
1 + "hello";      // 操作数类型不匹配
break;             // 不在循环中
```

Parser 能确认节点结构，却不知道一个名字指向哪个声明、一个运算符允许哪些类型、当前是否位于循环或函数中。阶段 2 新增的 semantic analysis 正是填补这层信息。

```text
AST
 |
 v
名字绑定：这个 Identifier 指向哪个 Symbol？
 |
 v
类型检查：这个 Expression 的 Type 是什么？
 |
 v
上下文规则：return / break / main 是否合法？
```

## 2. `SymbolTable` 为什么是一条父作用域链

词法作用域由源码的嵌套结构决定。一个块内部可以看到自身声明，也可以看到外层声明；离开该块后，内部声明不可见。

`SymbolTable` 因此保存当前作用域的名字映射和可选 `parent`：

1. `define` 只检查当前映射，阻止同一作用域重复声明；
2. `lookup` 先查当前映射；
3. 没找到就沿 `parent` 向外查；
4. 一直找不到才报告未定义。

这同时自然支持 shadowing：内层可以声明同名变量，查找会命中最近的一层；外层符号没有被删除，离开内层后又重新可见。

“变量使用指向程序文本中、最内层、先于该使用的声明”是词法绑定的经典定义；嵌套环境链也是其直接实现。参见 [Crafting Interpreters: Resolving and Binding](https://craftinginterpreters.com/resolving-and-binding.html)。

## 3. `Symbol` 与 `Type` 分别表达什么

`Symbol` 是一个已声明名字的语义身份，记录名字、种类、类型和声明位置等信息。它比字符串更可靠：两个不同作用域中的 `x` 文本相同，但应是两个不同的符号。

`Type` 表达表达式或声明的静态类型。阶段 2 的类型集合很小，反而便于看清算法：字面量产生固有类型，变量引用从 symbol 获取类型，运算符根据输入决定或验证输出类型。

另有一个特殊的 `ERROR` 类型。它不是用户可声明的类型，而是错误恢复哨兵。

### 为什么需要 `ERROR` 类型

若 `unknown` 已报告“未定义”，表达式 `unknown + 1` 不应再连带报告一串“加法左侧类型非法”。让失败子表达式返回 `ERROR`，父节点看到后继续传播但避免重复诊断，就能抑制级联错误。

## 4. `TypeChecker` 为什么要分多遍处理顶层

如果严格按源码从上到下“一遍走完”，前面的函数无法调用后面才声明的函数：

```xlang
fn main() -> int { return helper(); }
fn helper() -> int { return 42; }
```

阶段 2 先收集顶层函数和全局变量的名字/签名，再检查函数体与初始化表达式。于是检查 `main` 时，`helper` 已在全局符号表中。

这是一种小型多遍编译：

1. 声明遍：建立顶层可见名字；
2. 定义/检查遍：进入函数与表达式，验证具体语义。

它不是低效的重复劳动，而是在建立后续检查需要的前置知识。真实编译器也常将声明收集、名字解析和类型检查拆成不同遍。

## 5. 表达式类型是怎样递归算出来的

类型检查与 AST 结构天然匹配，因此仍然是一种树遍历：

- 整数字面量直接得到整数类型；
- 布尔字面量直接得到布尔类型；
- 标识符查符号表得到声明类型；
- 一元表达式先检查操作数；
- 二元表达式先检查左右子树，再按运算符规则验证；
- 调用表达式查函数符号，并逐个核对参数数量和类型；
- 赋值表达式检查目标存在、可赋值且类型兼容。

例如比较运算产生布尔类型，而算术运算产生整数类型。`if` 和 `while` 的条件则必须是布尔类型。

## 6. 为什么不用给 AST 节点直接加一个 `type` 字段

阶段 2 用 `IdentityHashMap<Expr, Type>` 保存“某个表达式节点对应的类型”，而不修改阶段 1 的 AST。

这样做有三个目的：

1. AST 仍是 Parser 的纯输出，不需要为了每个后续 pass 不断膨胀字段；
2. 同一个 AST 可在不同分析上下文中重复使用；
3. identity map 按节点对象身份区分，避免两个内容相等的 record 被错误视为同一处表达式。

这是一种 side table。编译器经常把类型、符号、常量值等派生信息放在独立表里。代价是使用者必须同时携带 AST 与检查结果，因此 `TypeCheckResult`/`CheckResult` 用于打包它们。

## 7. 语句和上下文规则如何检查

### 7.1 块作用域

进入块时创建 child symbol table，按顺序检查语句，退出后恢复 parent。局部变量只从声明之后可见；同一作用域重名会报错。

### 7.2 函数与 `return`

进入函数时记录期望返回类型，把参数定义到函数作用域。遇到 `return` 时对照当前函数签名；函数外出现 `return` 则没有合法上下文。

### 7.3 循环与 `break` / `continue`

检查器维护循环深度。进入循环递增，退出递减；深度为零时的 `break` 或 `continue` 非法。这个整数比保存完整循环 AST 更简单，因为本阶段只需回答“是否位于某个循环中”。

### 7.4 `main` 契约

工具链需要确定程序入口，因此阶段 2 验证 `main` 是否存在以及签名是否符合约定。这不是一般类型系统规则，而是 XLang 平台 ABI 的一部分。

## 8. 为什么语义错误仍然尽量继续检查

和 Parser 一样，TypeChecker 也追求一次给出多个互不依赖的错误。它把诊断收集到结果中，而不是遇到第一处错误就抛出异常。

不过“继续”不等于假装成功：最终结果明确标记是否存在错误，后端不得在类型失败后继续生成代码。恢复只为了改善诊断体验，不应把非法程序交给后续阶段。

## 9. 当前实现的边界与权衡

- 类型集合有意很小，没有泛型、子类型或类型推断；
- 作用域是词法作用域，不实现动态作用域；
- 顶层采用简单多遍，而不是建立复杂模块图；
- 表达式类型存 side table，换取 AST 不变性；
- 控制流返回检查是教学级实现，不等同于工业编译器的完整 definite-return 分析。

这些限制使“名字解析”和“类型推导/验证”两个核心问题足够清晰。

## 10. 建议你亲手验证

1. 在内外两个块各声明 `x`，观察引用各绑定到哪个 symbol。
2. 在同一块重复声明 `x`，与内层 shadowing 对比。
3. 让 `main` 调用定义在文件后方的函数，验证多遍收集的价值。
4. 输入 `unknown + true`，观察是否避免无意义的级联诊断。
5. 把 `break` 分别放在循环内外，追踪循环深度。
