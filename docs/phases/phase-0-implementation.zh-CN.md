# 阶段 0 源码实现分析：先搭起一条可以持续生长的工具链

> 对应提交：`阶段0：搭建多模块工具链骨架`
>
> 本文面向第一次接触编译器、虚拟机和链接器的开发者。阅读时建议同时打开根目录的 `settings.gradle.kts`、`build.gradle.kts`，以及五个模块中的入口类。

## 1. 这一阶段究竟解决什么问题

阶段 0 没有“编译”任何语言。它先回答一个更基础的问题：以后新增词法器、类型检查器、虚拟机和链接器时，代码应放在哪里，它们怎样依赖，怎样被同一套命令构建和测试？

最终系统的方向是：

```text
源代码 -> xlangc -> 目标文件 -> xld -> 可执行文件 -> xlangvm
                        ^                         |
                        |                         v
                       xrt <-------------------- XOS
```

阶段 0 只建立这些边界和入口。这样做的价值不是“文件整齐”，而是尽早固定依赖方向。编译器不应偷偷依赖命令行界面，虚拟机也不应反过来调用编译器内部实现。

Gradle 把一个构建拆成 root project 与多个 subproject，正适合表达这种模块关系；官方称每个 subproject 都能拥有自己的源码和配置，同时由一个构建统一协调。参见 [Gradle Multi-Project Builds](https://docs.gradle.org/current/userguide/intro_multi_project_builds.html)。

## 2. 五个模块各自负责什么

| 模块 | 长期职责 | 阶段 0 的状态 |
| --- | --- | --- |
| `xlangc` | 前端、语义分析、IR、后端 | 提供会明确报错的占位入口 |
| `xlangvm` | CPU、内存、操作系统模型、执行器 | 提供占位入口 |
| `xld` | 合并目标文件、解析符号、重定位 | 提供占位入口 |
| `xrt` | 语言运行库与 libc 风格包装 | 提供占位入口 |
| `xlang-cli` | 把上述能力组织成用户命令 | 提供真正可运行的 `Main` |

这里采用“CLI 是外壳，模块是能力”的结构。将来测试词法器时可以直接调用 `xlangc`，不必伪造命令行参数；测试 CPU 时也不需要先跑完整编译器。

## 3. 构建文件为什么这样写

### 3.1 `settings.gradle.kts` 是模块清单

`settings.gradle.kts` 用 `include(...)` 声明五个子项目。它不是普通的依赖列表，而是在告诉 Gradle：这些目录属于同一个构建，任务、依赖和产物由同一个项目图管理。

### 3.2 根 `build.gradle.kts` 集中约束工程质量

根构建对所有 Java 子项目统一设置：

- Java 21 toolchain 与 `--release 21`，避免“开发机 JDK 碰巧能编译，别的机器不能”；
- `-Xlint:all` 和 `-Werror`，把潜在问题提升为构建失败；
- JUnit Jupiter 与 `useJUnitPlatform()`，为后续每阶段的回归测试建立统一入口；
- `phaseInfo`，让当前实现阶段可被构建系统直接查询。

Java toolchain 的作用是声明构建需要的 Java 版本，而不是依赖当前 shell 中碰巧存在的 `java`。这是 Gradle 官方推荐的可复现构建机制，参见 [Gradle Java Toolchains](https://docs.gradle.org/current/userguide/toolchains.html)。测试运行方式参见 [JUnit 5 User Guide](https://junit.org/junit5/docs/5.11.0/user-guide/index.html)。

### 3.3 为什么占位实现要“失败得很响亮”

尚未实现的 `Xlangc`、`XMachine`、`Xld` 和 `Xrt` 不返回一个伪造成功结果，而是抛出或报告明确的 unsupported 错误。这叫 fail fast：错误应在离原因最近的位置出现。

如果占位编译器返回空字节，故障会延迟到链接器或虚拟机才暴露。届时开发者看到的是“程序没有输出”，而真正原因却是编译器根本没有实现。明确失败能保护模块契约。

## 4. 从命令行追踪一次真实调用

`xlang-cli` 中的 `Main` 是用户入口。阶段 0 的执行过程可以理解为：

1. `main(String[] args)` 接收参数；
2. 解析顶层子命令；
3. 对已知但尚未实现的命令，转交相应模块入口；
4. 模块明确报告当前阶段不支持；
5. CLI 将诊断和退出状态呈现给用户。

这里没有把所有实现写进 `Main`，因为 CLI 的职责只是输入输出适配。编译行为若埋在 CLI 内，后续 IDE、测试或其他程序就无法复用它。

## 5. Java 21 在架构中的作用

阶段 0 现在看不出 records、sealed classes 和模式匹配的价值，但后续 AST、XIR 和目标文件都会大量使用不可变数据模型。固定 Java 21，是在为这些表示形式铺路。

Record 用紧凑语法表达“主要由数据构成的透明载体”，sealed class/interface 则能限制一个层次结构有哪些合法实现。两者分别由 [JEP 395](https://openjdk.org/jeps/395) 和 [JEP 409](https://openjdk.org/jeps/409) 标准化。

## 6. 容易产生的误解

### “没有算法，所以阶段 0 不重要”

恰恰相反。后续每层都依赖这里确定的模块方向、Java 版本和测试入口。架构边界晚改，代价通常比局部算法晚改更高。

### “多模块只是把包拆成目录”

包名只提供语言级命名空间；Gradle 子项目还能形成构建级依赖和独立产物。两者解决的问题不同。

### “先全部写在一起，最后再拆也一样”

最后再拆时，循环依赖往往已经形成。例如 CLI 类型流入编译器 API、虚拟机读取编译器私有类。阶段 0 的边界能让这些问题更早暴露。

## 7. 建议你亲手验证

1. 运行 `./gradlew projects`，观察根项目与五个子项目。
2. 运行 `./gradlew phaseInfo`，确认构建能报告阶段状态。
3. 运行 `./gradlew build`，观察每个模块都进入统一生命周期。
4. 临时制造一个编译警告，确认 `-Werror` 会阻止它进入历史，然后撤销实验修改。
